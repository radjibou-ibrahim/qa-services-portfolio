# QA Quick Audit

> A focused manual QA review to identify functional issues, usability problems and potential risks before they affect users.

---

## Overview

The **QA Quick Audit** is a focused manual testing service designed to provide a practical quality assessment of a website or web application within a limited testing scope.

The objective is to quickly identify important issues that could affect users, business operations or the overall quality of the product.

This service is particularly suitable for startups, entrepreneurs, developers and small teams that need a first QA review without requiring a complete testing project.

---

# 🎯 Objectives

The main objectives of a QA Quick Audit are to:

- Identify functional defects
- Detect usability issues
- Verify critical user flows
- Check forms and input validation
- Identify unexpected application behavior
- Explore areas that may contain potential defects
- Provide clear and actionable QA feedback
- Help the product team prioritize identified issues

The audit focuses on **practical risk identification**, not exhaustive test coverage.

# 🧪 Testing Areas

Depending on the application, the audit may cover:

### Navigation

- Main navigation
- Internal links
- Back/forward navigation
- Menu behavior
- Broken or unexpected links

### Forms

- Required fields
- Valid inputs
- Invalid inputs
- Empty inputs
- Incorrect formats
- Boundary values when relevant
- Error messages
- Form submission behavior

### Authentication

When authentication is part of the agreed scope:

- Login
- Logout
- Invalid credentials
- Required fields
- Password-related behavior
- Redirection

### Functional Behavior

- Buttons
- Links
- User actions
- Data submission
- Add/remove actions
- Search functionality
- Filters
- Sorting
- Basic workflows

### User Experience

The audit may identify obvious usability issues such as:

- Confusing messages
- Missing feedback
- Inconsistent behavior
- Difficult navigation
- Unclear validation messages
- Unexpected user flows

Usability observations are reported separately from confirmed functional defects when appropriate.

# 🔄 Audit Process

The QA Quick Audit follows a simple process.

```text
1. Client Request
       ↓
2. Scope Definition
       ↓
3. Application Access
       ↓
4. Initial Exploration
       ↓
5. Test Execution
       ↓
6. Issue Identification
       ↓
7. Bug Documentation
       ↓
8. Evidence Collection
       ↓
9. QA Summary
       ↓
10. Delivery
```

---

## 1. Client Request

The client provides basic information about the product and the reason for requesting the audit.

### Examples:

- New application launch
- New feature validation
- Pre-release testing
- General quality review
- Verification after development work
- Identification of critical functional problems

---

## 2. Scope Definition

Before testing begins, the following elements are clarified:

- Application URL or access method
- Features to test
- User roles
- Main user flows
- Testing environment
- Test accounts, if required
- Testing deadline
- Expected deliverables

A clearly defined scope helps keep the audit focused and useful.

---

## 3. Initial Exploration

The application is first explored to understand:

- Main functionality
- User journeys
- Navigation structure
- Critical workflows
- Potential risk areas

This initial exploration helps determine where testing effort should be concentrated.

---

## 4. Test Execution

Tests are performed according to the agreed scope.

Testing may include both:

- predefined checks
- exploratory testing

The objective is to identify issues that could have a meaningful impact on users or the product.

---

## 5. Issue Identification

When an issue is discovered, it is analyzed to determine:

- Whether the behavior is reproducible
- The conditions under which it occurs
- The expected behavior
- The actual behavior
- The potential impact

Issues are then classified appropriately.

---

## 🐞 Bug Reporting

Each confirmed defect is documented clearly.

A typical bug report contains:

| Field | Description |
|---|---|
| **Bug ID** | Unique identifier |
| **Title** | Short description of the defect |
| **Environment** | Browser, OS, device, etc. |
| **Preconditions** | Conditions required before testing |
| **Steps to Reproduce** | Steps required to reproduce the issue |
| **Expected Result** | Expected application behavior |
| **Actual Result** | Observed behavior |
| **Severity** | Impact of the defect |
| **Priority** | Recommended urgency |
| **Evidence** | Screenshot or video when relevant |

The objective is to make each reported issue as clear and reproducible as possible.

---

## 📸 Evidence

When relevant, testing evidence may include:

- Screenshots
- Screen recordings
- Error messages
- Relevant UI states
- Reproduction evidence

Evidence is collected to support important findings and make defect investigation easier.

---

## 📊 Severity and Priority

Identified defects may be classified according to:

### Severity

The potential impact of the defect on the application or user.

**Examples:**

- Critical
- High
- Medium
- Low

### Priority

The urgency with which the issue should be addressed.

**Examples:**

- P1 — High
- P2 — Medium
- P3 — Low

Severity and priority are assessed according to the context of the application.

## ⏱️ Typical Audit Scope

A Quick Audit is intentionally limited in scope.

The audit does not automatically mean that every feature, browser, device or user flow has been tested.

Before starting the engagement, the testing scope is explicitly defined.

Examples of scope limitations may include:

- Specific pages
- Specific user flows
- Specific features
- One or more browsers
- Desktop only
- Mobile browser only
- A defined testing period
